## 3. New findings (R-series), ordered by priority

**R1 — reduced-motion players get HALF the reading time on every toast.**
`ui/toast.ts:10`: `const hold = (reducedMotion ? holdMs * 0.5 : holdMs) *
speedMultiplier;`. A text hold is not motion — this is precisely the
backwards logic the §1 interlude fix called out in its own comment
("shortening reading time under reduced motion would be backwards",
`flow.ts:72-81`), sitting unnoticed in the neighboring subsystem. The
player it hits hardest is the E3 profile-reset case: the single most
consequential notice in the game ("your save could not be read… nothing
could be recovered", 4200ms hold) displays for **2100ms** to a
reduced-motion player — likely under one read-through. The short
fade/show delays under reduced motion (lines 8, 11) are correct and
should stay; only the hold halving is wrong. **Fix plan:** drop the
`* 0.5` on the hold (keep the shorter fades), and extend the §6
pacing-constant guard class to toasts — the game-experience review itself
proposed "toast hold ≥ 1,500ms" as part of that one small test file, but
only the interlude half was ever written (`interludeTiming.test.ts`); add
the toast-hold assertions (all four named toasts ≥ their intended
minimums, and no reduced-motion multiplier on the hold) to close the
review's own §6 recommendation properly.

**R2 — "Reset all progress" doesn't actually erase everything it says it
does.** `flow.ts:429-433` (`resetProgress`) writes `defaultProfile()` and
reloads — but the cross-pack `vestibule:sharedDisplaySettings` key
(`sharedDisplaySettings.ts:12`) survives, and `main.ts:58` overlays it
unconditionally on every boot, so quality/renderScale/uiZoom/fpsCap
silently come back after a supposed full wipe. The Settings description
explicitly promises total erasure in all five languages (e.g. cs:
"Vymaže úplně vše — poznámky, konce, **nastavení**…"). Two defensible
resolutions; recommend the first: (a) clear `SHARED_KEY` inside
`resetProgress` so behavior matches the promise (one line + one test), or
(b) soften the description ×5 languages to exclude display settings.
Related, recorded not as a bug: the *other pack's* profile also survives
(storage is pack-namespaced by design) — arguably correct for a per-pack
reset button, but worth remembering if a player ever reports "reset
didn't reset the other game."

**R3 — door barks are invisible to screen readers.** Every beat played
through `playBeats` announces via `aria-live="polite"`
(`textPanel.ts:110`), but `showBark` (`textPanel.ts:272-277`) — the
guide's door-row one-liners, one of the most character-rich recurring
surfaces in the game — builds its `p.beat.usher` with no live region at
all, so a screen-reader player never hears the Usher/Porter speak at the
door row. One-attribute fix, mirroring the beat element.

**R4 — the end screen's "doors you never opened" shows the same doors
every run.** `flow.ts:1147-1150` filters `pack.rooms` (declaration order)
and takes `.slice(0, 3)` — so the teaser list is biased to the
earliest-declared unvisited rooms and will read near-identically across
runs for most players, undercutting T4's replay-hook intent. **Fix
plan:** salt-shuffle the candidates with the run's own `doorSeed` (the
exact pattern `storyEngine.ts:106-109` already uses for door offers) so
each run advertises different unopened doors. Small; pure; testable.

**R5 — carried forward, already planned:** E6 implementation (deferred
Examined Path offer — complete design in `15-game-experience-review.md`
§8) and N1 (end-screen data computed once before its action loop, so a
language switch via the new Settings button reshows stale-language text —
`flow.ts:1065-1150` all pre-loop; plan in §9 there). Both should ship as
one batch; R1-R4 above are small enough to ride along.

**S1 — "Your last message" displays in English for every non-English
player (real i18n bug, both packs).** `flow.ts:928` stores the hook-room
choice's *raw English source text* (`choice.text`) into
`profile.lastMessage`, and all three display surfaces render it verbatim:
the end-screen recap thesis (`flow.ts:1131`), the Ledger row
(`ledger.ts:132-133`), and the codex card + its synthetic "sender: you"
note (`overlays.ts:945-950`). A Czech player who clicked a Czech sentence
in `last-message`/`the-unsent` sees it echoed back **in English** on every
one of those surfaces, forever. The proof it's wrong is ten lines away:
the Morning Report's sibling path re-translates the same transcript data
correctly at display time (`t(roomChoiceTextKey(entry.roomId,
entry.choiceId), entry.choiceText)`, `flow.ts:1141`). **Fix plan:** store
the choice *id* alongside (additive optional `Profile.lastMessageChoiceId`
— no schema bump, `keepsakesHeld` precedent), and translate at each
display site via `roomChoiceTextKey(pack.hooks.lastMessageId, choiceId)`
with the stored raw string as fallback, so legacy saves (id absent)
degrade to exactly today's behavior. Also fixes the language-switch case
for free — display-time resolution always follows the current locale.

**S2 — Escape-close inconsistency across sibling overlays.**
`showCredits` (`overlays.ts:733-763`) has no Escape handling at all —
Back-click only — even though `showRoomArticle`'s own comment
(`overlays.ts:801-805`) claims it was made consistent "with every sibling
overlay (showAbout, showCredits, …)": the comment is wrong about the very
file it lives in. `showPersona` and `showExaminedPathOffer` also close
only via buttons — for those two it is arguably *deliberate* (each
demands an explicit answer; Escape has no obvious meaning), but nothing
records that as a decision anywhere. **Fix plan:** add the standard
`onEscape` to Credits (five lines, mirrors About); record
persona/Examined-offer as "no Escape by design — an answer is required"
in a comment, or give them Escape-as-Skip/Escape-as-default semantics if
the owner prefers; correct the article comment.

**S3 — locked codex cards are focusable dead buttons.** `showCodex`'s
`addCard` (`overlays.ts:901-931`) renders locked entries as `<button
class="codex-card locked">` with no click handler, no `disabled`, no
`aria-disabled` — a keyboard user tabs through dozens of inert buttons
(30+ rooms plus endings early on), each announcing only "· · · not yet
walked" with no cue that activation does nothing. **Fix plan:** set
`disabled = true` on locked cards (they are genuinely non-interactive),
which also removes them from tab order; the visual `.locked` styling
already exists.

**S4 — a failed profile import leaves the confirm button permanently
armed.** `confirmButton` (`overlays.ts:199-219`) never disarms after
`onConfirm` fires. For Reset-run (button disables itself) and
Reset-progress (page reloads) that's moot — but the Import button's
confirm path can *fail* (invalid JSON → status text, no reload,
`overlays.ts:495-503`), after which `armed` stays true with the timer
cleared, so every subsequent single click re-fires the import with no
"click again to confirm" step ever again. Two-second fix: call the
existing `disarm()` at the top of the confirmed branch.

**S5 — smaller nits, one line each.** (a) The Settings language row

## 10. Targeted bug hunt (same day): three verified finds, three cleared hypotheses

Owner directive: find three *additional* game-breaking or annoying bugs —
"do not make anything up." Method: instead of more breadth, this hunt went
depth-first into the three places state machines cross, where this
codebase's own history says bugs live: (1) the run-completion/persist
boundary, (2) timing contracts between JS waits and CSS transitions, (3)
input-modality asymmetries (pointer vs. keyboard) and layered-overlay
input routing, plus (4) cross-pack profile-import data flows. Every
hypothesis was verified against the code before being written down —
including the ones that turned out to be **wrong**, recorded below so the
clean areas stay marked clean.

**H1 — keyboard-only players get a completely silent game (annoying,
accessibility).** The AudioContext is primed by exactly one listener in
the whole codebase: `addEventListener('pointerdown', () =>
sound.primeOnGesture(), { once: true })` (`flow.ts:219`). The context
itself is created at boot with no gesture (the title-music path calls
`ensureCtx()`, `soundEngine.ts:199/211`), so the browser's autoplay
policy starts it `'suspended'` — and the only `resume()` calls anywhere
are `primeOnGesture` (`soundEngine.ts:278-283`, pointerdown-only) and the
`visibilitychange` handler (`soundEngine.ts:322`), which runs outside
user activation and therefore *cannot* un-suspend a policy-suspended
context. A `keydown` is a perfectly valid activation gesture the app
never uses for audio. The sting: this game ships first-class keyboard
play — arrow-key navigation (9.5.3), focus traps (9.5.1), and UAT 25
proves an entire door/choice flow keyboard-only — and every one of those
players hears no music, no door chimes, no heart-loss cue, ever, with no
error anywhere. The codebase already learned this exact lesson for
fullscreen resume (`fullscreen.ts:78-80` listens on
click+keydown+pointerdown with a shared one-shot guard); audio never got
it. **Fix plan:** mirror that triple-listener for `primeOnGesture` — two
lines beside `flow.ts:219`.

**H2 — the "Explain this simply" button is unreachable by keyboard (and
the back arrow and beat dots with it).** `waitAdvance`'s window-level
keydown handler (`textPanel.ts:227-238`) treats every Space/Enter as
"advance the beat" — `e.preventDefault()` plus `onForwardClick()` — with
no check of what currently has focus. A keyboard user who Tabs onto the
`?` explain button (a real, focusable `<button>`) and presses Enter or
Space advances the beat instead, and the `preventDefault()`
simultaneously suppresses the button's native activation, so the
explanation can never open. The same swallow hits the `‹` back button
(its ArrowLeft shortcut still works; the visible button itself is dead).
And the beat-progress dots (`textPanel.ts:117-123`) carry `role="button"`
and an aria-label but no `tabindex` — announced to assistive tech as
buttons, reachable by nothing. The bug class is *known* in this codebase:
`fieldNote.ts:92` guards its read-more button with exactly the missing
check (`document.activeElement !== readMore`). Net effect: the feature
built specifically for accessibility — plain-language explanations of
each dilemma — is inaccessible to precisely the input mode that needs
guards most. **Fix plan:** in `waitAdvance`'s onKey, let Space/Enter pass
through untouched when `document.activeElement` is one of the panel's own
interactive children (explain, back, dots), mirroring fieldNote's guard;
give the dots `tabindex="0"` (they already have role and label).

**H3 — E4 regression: the end screen's Settings offers "Reset current
run" for a run that no longer exists.** `inGame` is set `true` at run
start (`flow.ts:551,630`) and **never cleared** — so
`settingsActions().hasRun` (`flow.ts:469`: `this.inGame || …`) is still
`true` on the end screen, where the finished-run persist has already
nulled `profile.run` (`flow.ts:1102` sets `finished`, `flow.ts:372` nulls
on persist). Until this cycle that was unobservable — Settings wasn't
reachable while `inGame` with no live run. E4's new end-screen Settings
button made it reachable: the panel now shows an armed, danger-styled
"Reset current run" control whose own description promises to abandon
"your in-progress journey" — which doesn't exist. Confirming it fires
`resetRun()` → reload → title: no data is lost (everything already
persisted), but the recap/Morning Report screen the player was reading
vanishes without warning, and the control is a lie either way. **Fix
plan:** `hasRun: (this.inGame && !this.state.finished) ||
Boolean(this.profile.run && !this.profile.run.finished)` — one line —
plus a source-shape test asserting the finished-state condition.

**Hypotheses that FAILED verification (recorded so clean stays clean):**
(1) *"`state.finished` is never set, so a finished run re-offers
Continue and double-counts `runsCompleted`"* — *wrong*: `flow.ts:1102`
sets it before the stats persist, and quitting mid-ending-beats resumes
into the final room and re-evaluates cleanly with a single increment.
(2) *"A cross-pack profile import crash-loops the title screen via the
epitaph wall dereferencing foreign ending ids"* — *wrong*: both packs'
`epitaphLines` filter unknown ids (`endings.ts:82-91`,
`limerence/index.ts:170-177`), with a comment showing imports were
explicitly considered. (3) *"The veil's JS waits and CSS transition
disagree under reduced motion, popping the theme swap into view"* —
*wrong*: 720ms JS vs 700ms CSS and 280ms vs 250ms
(`flow.ts:400`, `styles.css:195-200`) — correct 20-30ms settle margins in
both modes. Also verified clean on the way: the recovery overlay is
properly `.overlay`-classed (in-game key guards all see it), and
`showExplanation`'s dismiss-on-any-key is intentional (its close button
holds focus).
